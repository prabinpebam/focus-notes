Experience

Desktop app

A title bar you can't see until you need it, with the trigger in the middle. On Windows and Linux the window has 20 px corners and app-built window management; on macOS it's a native window.

TL;DR

The Electron app is a dedicated desktop experience and the only client that saves notes to GitHub; the web app on each instance's own GitHub Pages is where you start, keeping its own notes in the browser (D-80, D-90). It's downloaded from GitHub Releases. On every platform the top 44 px is an invisible title bar with the trigger centered across it, just below (40 px from the top edge, D-78), and the window controls appear only on hover or keyboard focus. In full screen the band hides until the pointer reaches the top edge. macOS also has a full native menu bar, built from the app's commands. Windows and Linux: a transparent, frameless window with 20 px rounded corners. Electron's transparent windows lose native resizing, snapping, maximize, and the shadow, so the app rebuilds all of window management itself: moving, resizing, maximize and restore, edge and corner snapping, a Snap Layouts picker, a system menu, the shadow, and multi-monitor handling. macOS: a native window with the system's own corners, shadow, resizing, full screen, and tiling, and no 20 px requirement (owner decision D-14). Covers DSK-01 to DSK-08 in the requirements.

Window management on Windows and Linux

Electron documents that transparent windows aren't natively resizable, can't be maximized from the Windows system menu or by double-clicking the title bar, have no native shadow, and can't use the native title-bar overlay. Native edge snapping and Snap Layouts don't apply to them either. The app rebuilds each of these (DSK-03, DSK-08):

BehaviorHow the app provides it
MoveDragging anywhere in the title bar band moves the window. The app handles the drag itself (pointer capture, with the new position applied once per frame) so it can detect screen edges for snapping.
ResizeInvisible handles on all four edges (6 px) and corners (14 px), with the right resize cursors. They lie in the shadow margin just outside the window, or just inside its edges when it's snapped; a maximized or full-screen window has none. Minimum size is 480 × 360. Holding Shift while resizing keeps the proportions. A snapped window resized by hand becomes a normal window where it is.
Maximize and restoreThe maximize button, double-clicking the band, dragging to the top edge of the screen, or > Maximize window. Dragging the band of a maximized or snapped window (by at least 4 px) restores it under the pointer at the same relative position, as Windows does.
MinimizeThe minimize button, or clicking the taskbar button (system).
Edge snappingDragging to the left or right screen edge (within 8 px) previews a half-screen zone, a corner (within 64 px of it along the edge) previews a quarter, and the top previews maximize. An edge shared with another display isn't a snap edge, so the window can cross to it. The preview is a translucent accent rectangle (cmp.windowFrame.snapPreview at 30%), drawn by the app in a click-through window of its own behind this one, and releasing applies it. The zones use the display's work area, so the taskbar is never covered.
Snap Layouts pickerHovering the maximize button for 400 ms (or pressing ↓ while it has keyboard focus) shows a small picker modeled on Windows 11: halves, thirds (on work areas at least 1920 px wide), quarters, and maximize. The arrow keys move between the zones, Enter chooses one, and Esc goes back to the button. Every zone is at least 24 × 24 px (WCAG 2.5.8), so each layout is 84 × 56 px, and in a narrow window the layouts wrap. Choosing a zone places this window there. It doesn't form a snap group with other apps' windows, which only Windows can do.
System menuAlt+Space, or right-clicking the band, opens an app-drawn window menu: Restore, Move, Size, Minimize, Maximize, Snap left, Snap right, Close. It opens on its first item that applies (Move, while the window isn't maximized and Restore is unavailable); the arrow keys still reach the unavailable ones. Move and Size work with the arrow keys (10 px a press, 1 px with Ctrl), Enter to keep and Esc to put the window back, like the Windows system menu; Size's first arrow chooses the edge. Close shows Alt+F4.
Keyboard snappingWin+arrow keys belong to Windows, and the app can't take over the Win key. The same moves are commands (> Snap window left, > Snap window right, and one for each third and quarter), with Snap left and Snap right in the system menu. Whether Windows applies Win+arrows to this window is checked by hand (D-104).
ShadowA soft CSS shadow (shadow.1) and a hairline border, drawn in a 16 px transparent margin around the window. The margin passes clicks through to whatever is behind it, so it never blocks other apps: the page tells the main process when the pointer moves near the window's edges, and the main process checks it against the margin and the handles and ignores the mouse over the rest of the margin. On Windows the system still forwards pointer moves to the page; Linux can't, so there, only while the pointer is in the margin, the main process checks it every 50 ms until it leaves. Nothing checks the pointer at rest (PRF-04). It goes away when maximized, snapped, or full screen.
Multiple monitors and scalingPositions and sizes are calculated for each display's work area and scale factor. Moving to a display with a different scale re-measures the window so it keeps its physical size: a move sets only the window's position, and afterwards its size in device-independent pixels (about the same size on screen at each display's scale) is put back if the system changed it. A window that would open off-screen is moved onto the nearest display.
Full screenF11: the window covers the whole display, and corners and shadow go away (the app keeps full screen itself, because Electron doesn't for transparent windows). The title bar band hides until the pointer reaches the top edge (Window behavior). The trigger stays visible.

Checked by hand

The journeys drive the window through the app's own handling: screen positions given to the window frame, the controls, the picker, and the menu. What only a real desktop shows is in the M2 demo on Windows 11, Windows 10, and Ubuntu: dragging with a real pointer and snapping at every edge and corner, Win+arrows, Alt+Space opening only the app's menu, the click-through margin, moving between monitors with different scaling (D-104), and the full-screen band coming back with a real pointer at the top of the display. On a Mac: the traffic lights following a real pointer on the band, each menu bar key running its command once on a real keyboard, and Help's search finding commands (D-106).

Title bar

Band
The top 44 px of the window (layout.titleBar). It's invisible: the same color as the canvas, with no line under it. When the note scrolls, its text passes under the band and the frosted trigger.
Drag
The whole band moves the window, except the trigger, the window controls, and any open panel. On macOS this is the system's drag region. On Windows and Linux it's the app's own move handling (above).
Trigger
Centered horizontally across the band, 40 px below the window's top edge (owner decision D-78, see Main UI), so it sits just under the band rather than inside it (D-106). It's never part of the drag region. This is its only position, and it doesn't move when the window is resized.
macOS controls
The native traffic lights, positioned to sit comfortably in the band. They sit 16 px from the left and 14 px from the top (window.trafficLightX, window.trafficLightY). They're hidden at rest and appear when the pointer enters the band, when the toolbar is open, when the window isn't the active one, and in full screen, where the system shows them with the menu bar. The band is the system's drag region, which gives the page no pointer events, so the page tells the main process when the pointer comes near the band or leaves the page, and the window's focus, blur, and full-screen events do the rest; only while the pointer is on the band, or just under it, in the active window does the main process check it, every 100 ms, until it leaves, setting the native window-button visibility. Nothing checks the pointer at rest (PRF-04). A pointer that comes onto the band straight from outside the window, without passing the page, shows them once the window is clicked or the pointer moves through the page. They can't take keyboard focus; the Window menu has their commands. Double-clicking the band follows the user's system setting (zoom or minimize).
Windows and Linux controls
Minimize, maximize/restore, and close, drawn by the app at the top right in theme colors, with a red hover state on close following the Windows convention. They follow the same show-on-hover rules as on macOS. They're real buttons that can be focused and have accessible names. Hovering maximize for 400 ms opens the Snap Layouts picker (D-15). They have no tooltips, since hovering maximize opens the picker.
Keyboard
Every window action is also a command: > Minimize window, > Maximize window, > Snap window left, > Close window, > Toggle full screen, with the usual shortcuts (App and window).

macOS menu bar

The menu bar is generated from the command registry, so it can't disagree with the keys, the toolbar, or the ⋯ menu (DSK-05, D-106). Each command is in it once, with its name, its macOS key from the keymap, and its state: a checkmark for a command that's on (Focus mode, Sync appearance), a radio mark for the chosen appearance, themes, and font, and dimmed while it can't run. Choosing an item runs the command in the app, like a toolbar button. The system's own items do the system's work. The ⋯ menu's items whose feature comes later (Share and visibility…, Help and docs) are there too, dimmed, and say why when the pointer rests on them, as they do in ⋯.

Commands that aren't in it are named in the registry's list with the reason: values and events views send, keys of one focused control (the find bar's options, a table's cells, the Files tree), buttons of an open panel, dialog, or context menu, the browser's own commands, the app-built window's commands (Windows and Linux), and Spotlight until it arrives. A test fails when a new command is in neither list. Keys reach the page first: a menu item chosen by its key just after the page saw that key press isn't run again, so each key runs its command once, and a key that belongs to a field with focus stays there.

Light, dark, and system

The window follows the same three-way theme choice as the rest of the app (Theming): System (default, follows the OS live), Light, or Dark. The native parts (macOS traffic lights and menus, context menus, the Windows taskbar thumbnail) follow it too, because the app sets Electron's native theme to match.
