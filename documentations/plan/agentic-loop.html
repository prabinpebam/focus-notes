Plan

The agentic loop

How AI agents, working with the owner, carry Focus Notes from this spec to the definition of done: the roles, the work graph they read, the loop each work package goes through, the evidence it leaves, and when the loop stops to ask a person.

TL;DR

The plan is a graph: work-graph.json lists 61 work packages with their requirements, dependencies, code areas, and required reviews. An orchestrator agent picks a work package whose dependencies are done and briefs it against the definition of ready. A builder writes the tests first, then the code and view documents. A verifier runs every gate and checks the evidence against the definition of done. Up to four reviewers (code, design system, accessibility, security) approve or send it back. After at most three rounds of fixes, or whenever a decision is needed, the loop escalates to the owner. Merged work updates the graph and the docs, and the next ready package starts. When a stage's packages are all done, the stage gate runs the demo, and the owner accepts it. The loop ends when the project definition of done is met.

Each role has an instruction file in .github/agents/, written in WP-0.1 and improved at every stage retrospective. All roles also follow the repository's AGENTS.md. A role can be played by different agents or models, but one agent never builds and reviews the same work.

The work graph

work-graph.json is the plan in machine-readable form, kept in step with the implementation plan (the plan check fails CI if they disagree). Each work package has an id, stage, title, summary, requirements, dependsOn, touches (code areas), reviews, specs (the pages to implement), lookahead, and status.

RuleDetail
ReadyEvery dependsOn package is done, the previous stage's gate has passed (unless lookahead), and the brief meets the definition of ready.
Parallel workUp to three work packages run at once, and only when their touches lists don't overlap. Work on the critical path goes first.
Statusesplanned → ready → building → verifying → reviewing → done, or blocked with a reason and an escalation.
CoverageThe plan check fails CI unless every requirement belongs to exactly one work package, every dependency exists in the same or an earlier stage, and the graph has no cycles.
ChangesSplitting a work package keeps its ID as the parent (WP-1.5a, WP-1.5b). Moving requirements between stages follows Changing the plan.

The loop, step by step

  1. 1. Select

    The orchestrator lists ready work packages and picks the one on the critical path, or the oldest. If none are ready, it reports what's blocked and why.

  2. 2. Brief

    It writes the brief: the requirements with their user-can and acceptance criteria, the spec sections, the test names for every acceptance check, the view-document outlines, and any new component, token, command, dependency, or network destination. A spec gap or contradiction stops here and goes to the owner.

  3. 3. Build

    The builder writes the failing tests first, then the smallest code that passes them, in pull requests of about 400 lines or fewer. UI is built only as view documents and catalog components.

  4. 4. Verify

    The verifier runs every gate on three platforms (tests, journeys, ui:check, visual regression, axe, budgets, CodeQL, the license check) and fills the evidence record. Any missing evidence counts as a failure.

  5. 5. Review

    The reviews the work package lists run in parallel. Each approves or requests changes with specific references. Changes go back to Build.

  6. 6. Integrate

    The change merges to main, the nightly build is checked on all three platforms, the docs keeper updates the spec pages and the graph, and the orchestrator recomputes progress.

  7. Stage gate

    When every work package in a stage is done, the verifier runs the stage definition of done, a preview release is built, and the owner runs the demo script. Acceptance opens the next stage.

Escalation

The loop stops and asks the owner when:

  • The spec is missing, ambiguous, or contradicts itself, or a decision is needed. The question comes with options and a recommendation.
  • A work package fails verification or review three times.
  • A change would add a network destination, stored personal data, a permission, or a dependency under a case-by-case license.
  • A test, budget, or visual baseline would need to be weakened or changed.
  • Anything touches credentials, sealing, publishing, or agent permissions in a way the threat model doesn't already cover.
  • A stage is ready for its gate.

Guardrails and progress

  • Never skip a gate, never merge red, and never mark something done without evidence.
  • Never edit seed-specs.md, and never change a requirement to match the code. Change the spec through the chain and a decision.
  • main is always releasable, and a change that breaks the nightly build is reverted first and fixed second.
  • Progress is measured, not estimated: for the current stage, the share of its requirements passing their acceptance checks, the gates that are green, and the demo steps that pass as journey tests. For the project, the stages that have passed their gates.
  • The loop ends when the project definition of done is met, and not before.
