# Risks

What could make Focus Notes fail, how likely and how bad each risk is, and what the plan does about it. Review this register at the end of every milestone.

> [!NOTE]
> **TL;DR.** The biggest risks are **scope** (a large product for a small team), the **custom window management on Windows**, **Markdown round-trip fidelity** with a rich editor, **supply-chain trust** (users' *Deploy app* workflows deploy the project's released bundle with their secrets present), **share passcodes** that can be attacked offline, **onboarding friction** (making a token in the browser; Git, sign-in helpers, and unsigned builds for the desktop app), **dependence on GitHub**, **the cost of running Git** for every view, and the **data-driven interface** turning into an inner platform or slowing feature work. Each has a mitigation and an early check in the roadmap.

| ID | Risk | Likelihood | Impact | Mitigation | Checked in |
| --- | --- | --- | --- | --- | --- |
| R-01 | **Scope is large for a small team.** Version 1.0 includes the web app with sync, files, publishing, and sharing; the desktop app follows (D-85). | High | High | The milestones each ship something usable. P1 items are strictly deferred. Cut candidates are listed in the roadmap's definition of done. | Every milestone |
| R-02 | **Custom window management on Windows feels non-native** (resize jitter, DPI bugs, snapping fidelity, accessibility of the custom controls). | Medium | High | The M0 spike across Windows 10, Windows 11, and Ubuntu with mixed-DPI monitors. Use proven building blocks (pointer capture, Electron's screen APIs). Accessibility tests for the controls and the system menu. | M0, M3 |
| R-03 | **Markdown round-trip fidelity** with a rich editor (whitespace, list markers, escapes, tables) | High | High | The byte-for-byte corpus from M0. Untouched blocks are written back from their source text. Constructs that can't be kept are preserved as raw blocks. | M0, M1 |
| R-04 | **Supply-chain compromise** of the *Deploy app* workflow, the web app bundle, or the desktop releases, which run with users' secrets | Low | Severe | Pinned commit SHAs, pinned versions, checksums, attestations, signed builds, updates by pull request only, protected release environment, two-factor authentication on the maintainer account | M0, M5 |
| R-05 | **Share passcodes cracked offline** (static hosting can't rate-limit) | Medium (for weak passcodes) | High | Generated passcodes by default, a strength check for custom ones, PBKDF2 at 600,000 iterations, expiry by default. Users are told sealed sharing isn't for regulated or confidential material. | M5 |
| R-06 | **Onboarding friction:** copying the template and making a fine-grained token in the browser; for the desktop app, no Git, no sign-in helper on macOS or Linux, unsigned-app warnings | High | Medium | Pre-filled GitHub links and plain error messages in *Connect GitHub*, clear steps in *Use this app for yourself* and the README, install help in the desktop first run, three sign-in paths, signing budget planned before 1.0 | MW, M3, M5 |
| R-07 | **Git conflicts and repository states** confuse non-technical writers, or lose work | Medium | High | Note-level conflict choices, never leaving a rebase half-done, the recovery journal, Recently deleted, and integration tests for every repository state | M2, M3 |
| R-08 | **Dependence on GitHub:** API or Pages changes, rate limits, account suspension, the 60-day schedule rule | Medium | High | Plain Markdown in Git means any Git host keeps the notes readable. Conditional API requests and backoff. Keepalive warnings. GitHub.com only is a documented boundary (UNSUP-PLAT-01). | Ongoing |
| R-09 | **Private-note leaks** through publishing, XSS, or agents | Low | Severe | Leak check on every deploy, sanitization and CSP, agents denied private access by default, security review before 1.0 | M5, M7 |
| R-10 | **Prompt injection through note content** leads an agent to misuse its tools | Medium | Medium | No destructive or sharing tools, content labeled as data, attribution, and Undo | M7 |
| R-11 | **The public instance repository reveals metadata** (the private repository's name, publish times) | Certain | Low | Documented in the privacy commitments. The private repository can have any name. | M5 |
| R-12 | **Electron size, memory, and battery** expectations | Medium | Medium | Performance budgets enforced in CI by `pnpm bench --check`, no polling, lazy-loaded views, a warm-up that yields to typing | M1 onward |
| R-13 | **Licensing changes upstream** (for example Tiptap) | Low | Medium | Pinned versions (MIT releases stay MIT), the license check in CI, a plain ProseMirror fallback | Ongoing |
| R-14 | **Accessibility gaps** in custom widgets (the trigger, tables, window controls) | Medium | High | ARIA Authoring Practices patterns, automated and manual screen-reader passes every release | M1 onward |
| R-15 | **Workspace format drift** between app versions on different computers | Medium | Medium | `formatVersion`, migrations, and older apps refusing to write newer formats | M2 |
| R-16 | **The view format becomes an inner platform**: views need logic the format can't express, and pressure builds to add scripting | Medium | High | Logic belongs in view-model selectors and commands by design. The expression subset is fixed and growing it needs a decision. The M0 spike builds the three hardest views (Settings, Files, Spotlight) before the format is frozen. | M0 |
| R-17 | **Strictness slows feature work**: every new look needs a component change | Medium | Medium | A short component process, a broad initial catalog, variants before new components, and the gallery so changes are cheap to review | M1 |
| R-18 | **Renderer overhead** on large views | Low | Medium | Per-field subscriptions, virtual lists, fragments expanded at build time, the typing path outside the renderer, and DSY-11 budgets measured in the M0 spike | M0 |
| R-19 | **Git process cost makes the app feel slow**, especially on Windows, where each process costs about 80 ms and a dozen status questions per view add up to seconds | High | High | One cached `git status` per repository, run in parallel, that no view waits for (D-66). Structural changes shown before the commit (D-68). The benchmark counts Git processes per interaction and fails CI on a regression (D-65). | M0, M3 |
