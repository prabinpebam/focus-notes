Design system

Design system

One strict, layered system builds every pixel of Focus Notes: tokens, primitives, layouts, compound components, fragments, and views. The app's interface is data. JSON view documents are mapped onto the catalog's components, so no app code contains HTML or CSS.

TL;DR

Six layers, each allowed to use only the layers below it. Tokens (data) hold every visual value. Primitives and layouts are the only code that renders DOM elements or carries styles, and they style themselves only with tokens. Compound components are code that composes primitives and layouts, with no markup or styles of their own. Fragments and views are JSON documents that place components, bind them to typed view models, and run commands. Every component publishes a machine-readable contract, and the view schema is generated from those contracts, so a view that names an unknown component, prop, token, command, or string fails ui:check, which CI runs on every change. There is no escape hatch: a need the catalog can't meet becomes a new component, reviewed and tested, never inline markup. The owner set this direction (D-56, D-57). The rules below are what make it hold, and Enforcement says which check holds each one and which guarantees are still planned.

Two kinds of code sit beside the stack and never produce UI. View models are typed, read-only state with named selectors (the file tree, the current theme, the save state). Commands are the single registry of actions that the keyboard, Spotlight, menus, agents, and deep links already share (Keyboard shortcuts). A view reads view models and runs commands. It never computes, fetches, or decides anything itself.

The rules

  1. Every visual value is a token

    Color, size, space, radius, type, line height, shadow, blur, opacity, border width, motion, layer order, and breakpoints are all tokens. The only values that aren't tokens are measured at run time (an anchor's position, the focus band's height), and only primitives and layouts may apply them (DSY-02).

  2. Tokens alias down, never across or up

    Component tokens alias semantic tokens, and semantic tokens alias reference tokens. Components read only their own component tokens. Themes override semantic tokens only (DSY-01).

  3. Only primitives and layouts touch the DOM and styles

    They are the only files that render elements or declare styles, and they all live in packages/ui. Compound components compose them and nothing else (DSY-04).

  4. Every component has a closed contract

    Props are typed and enumerated: variants by name, sizes and spacing by token name, text as message keys, and actions as events. There's no className, no style, no pass-through of raw attributes, and no children of undeclared types (DSY-05). ui:check holds views to the contracts; holding each component's React props to its contract is planned (DS-A05).

  5. The app's interface is data

    Every view, including the visitor view and the published pages, is a JSON document rendered by the UI runtime. Application code is view models, commands, and services, with no markup or styles (DSY-06).

  6. Views carry no logic

    A view may bind, repeat, show conditionally through a small set of expressions, and run commands or set local state. Anything more becomes a view-model selector or a command, which can be tested on its own (DSY-07).

  7. Actions are commands

    Toolbar, menu, and Spotlight items reference command IDs. The label, icon, shortcut, and enabled or checked state come from the command registry, so a command reads the same everywhere (DSY-12).

  8. Accessibility is built in, not added

    Components implement the ARIA Authoring Practices patterns. Contracts make the accessible name required (an icon button needs a label, a dialog needs a title, a field needs a label), so a view can't leave it out.

  9. Nothing ships unvalidated

    ui:check validates every view against the generated schema, resolves every reference, type-checks every binding (list items included), and runs the accessibility and design rules. It runs in pnpm check, and any failure fails CI (DSY-08).

  10. No escape hatch

    There is no raw-HTML component, no style override prop, and no "custom" node type. A need the catalog can't meet goes through the component process.

Enforcement

Each rule below names the executable check that holds it and what that check covers today. Enforced means a check fails on every violation within the stated scope; Partial means a check exists but covers less than the rule; Planned means no check exists yet, and the audit finding that tracks it is named. pnpm check, pnpm typecheck, pnpm test, and pnpm test:e2e all run in CI on Windows, macOS, and Linux, and a failure on any of them fails the run (D-196). For how these checks were found wanting and fixed, see the design-system audit (19 October 2026).

Adding or changing a component

  1. Prove the need

    Show the view that can't be built from the catalog and the user-can it serves. Prefer a composition over a new variant, and a new variant over a new component.

  2. Write the contract and the decision

    The contract (props, variants, events, slots, states, tokens, accessibility pattern) and a design decision that traces to the user-can. Add the component's guidance row to Components, marked Implemented, and regenerate its inventory (node tools/component-inventory.mjs); pnpm check fails until both agree with the contracts (D-200).

  3. Add tokens first

    New component tokens alias existing semantic tokens. A new semantic token needs its own decision, because every theme then has to set it or inherit it.

  4. Build, fixture, and test

    The implementation in the right layer, a fixture for every variant, every declared state covered by a fixture or a named journey or listed as a gap with its reason (D-198), and keyboard and screen-reader behavior. Approved visual baselines will be required once the pixel gate exists (planned, DS-A03).

  5. Version the schema

    Additions are a minor change. Removing or renaming anything is a major change to the UI schema version, and it ships with an automatic migration for every view document (DSY-10).

Design decisions

IDDecisionServesRationaleAlternatives rejected
DD-DSY-01Six layers, each using only the layers below it, with markup and styles confined to primitives and layouts.UC-THEME-09, UC-CANVAS-02With one place for the look, a theme, a contrast fix, or a platform tweak changes every surface at once. That keeps the interface calm and consistent (CP-CALM-01).Shared CSS plus conventions, which drifts as soon as a deadline arrives.
DD-DSY-02Views are JSON documents, not code.UC-AGENT-06, UC-READ-01Data can be validated completely, diffed, migrated, read by agents, and rendered to static pages, and it can't hide one-off styling (D-57).Views as components in code, which allows exactly the exceptions the owner wants ruled out.
DD-DSY-03Compound components may not render elements or declare styles.UC-CANVAS-02It closes the gap where most design systems leak: a compound adding a margin or a color "just this once".Letting compounds style their own parts, the common pattern.
DD-DSY-04No escape hatch in views.UC-CANVAS-02Under pressure, an escape hatch becomes the main path. The component process is short enough to use instead.A RawHtml component or a style prop for emergencies.
DD-DSY-05Command-driven controls: toolbar, menu, and Spotlight items name a command, never their own label and icon.UC-KEY-02, UC-CANVAS-05The same action reads the same on every surface, with its real shortcut and state (CP-FLOW-01).Labels written in each view, which drift from the shortcut and from each other.
