Architecture

Repository and publishing

One public repository, one private submodule, and a GitHub Pages build that never publishes private plaintext.

TL;DR

The public repository holds the app, the docs, and public notes. Private notes live in a separate private repository mounted as a Git submodule at private/, the same pattern as the personal-site project. GitHub Actions checks out both repositories (the private one with a read-only deploy key), builds the app and public note pages, seals any privately shared notes with AES-256-GCM, checks that no plaintext leaked, and deploys to GitHub Pages. Readers of shared private notes decrypt them in their own browser using the key in the link's #fragment.

Two repositories

Public repository (this repo)

  • App source and build configuration
  • Public notes in content/
  • Custom themes and synced settings in .focus-notes/
  • Documentation (documentations/) and the slate/ submodule
  • The deploy workflow
  • A pointer (gitlink) to a commit of the private repository, plus .gitmodules

Private repository (submodule at private/)

  • Private notes and their assets/
  • access.json: share grants (secrets live only here)
  • Optional access-message.json: templates for sharing messages
  • Must never be made public

The public repository tracks only the submodule pointer, never the private files. This follows the personal-site setup, where .gitmodules declares the private repository with branch = main.

Working with the submodule

  1. Clone

    git clone --recurse-submodules, or run git submodule update --init after cloning. Without access to the private repository the submodule stays empty and the app still builds and runs with public content only (PKG-04).

  2. Track main

    A setup script switches private/ from detached HEAD to main and turns on recursive pulls and push checks (submodule.recurse, push.recurseSubmodules=check), as personal-site does.

  3. Commit private first

    Any change to private notes is committed and pushed to the private repository before the public repository's pointer is updated. A pointer must never reference a private commit that hasn't been pushed.

How the web app writes

The web app can't run Git, so the GitHub API adapter does the same thing through the REST API:

  1. Public note change: one commit to the public repository (contents API for single files, git trees and commits API for batched moves).
  2. Private note change: a commit to the private repository, then a commit to the public repository that updates the private gitlink (tree entry mode 160000) to the new private commit SHA.
  3. Visibility change: add the note to the target repository, delete it from the source repository, then update the pointer. Private side first, as always.

Bumping the pointer on every private save would trigger a public deploy (and a public commit) for every keystroke pause. Proposed (D-07): update the pointer only when the private change affects publishing (share grants or shared notes), plus once a day. Ordinary private edits stay in the private repository.

Deploy pipeline

Triggers
Push to main, manual dispatch, and a nightly schedule so share-link expiry takes effect without a push.
Private checkout
The Actions secret PRIVATE_CONTENT_KEY holds an SSH deploy key whose public half is installed read-only on the private repository. The workflow rewrites the submodule URL to SSH, runs git submodule update --init --depth 1 private, checks that private/access.json exists (refusing to deploy a half-configured site), then deletes the key from the runner.
Build logs that could reveal private note names are sent to a runner-local file instead of the public Actions log.
Build
Builds the app bundle, renders every note in content/ to a static page at /n/<path>/, and optionally publishes this documentation at /docs/.
Seal
For each active grant, encrypts the granted notes and their media into _sealed/<build>/ and writes the grant keyrings into _access/<build>/.
Verify
A leak check scans the output for any private text or file names and fails the deploy if it finds any.
Deploy
Uploads the verified artifact to GitHub Pages. Only main deploys.

Sealing and share links

This design follows the personal-site access spec, scaled down to what SHR-05 needs (magic links only, no typed access codes in the first version).

AspectDesign
Content encryptionAES-256-GCM with authenticated additional data (build ID, note ID)
KeysFresh random keys and build ID on every deploy. Per-note and keyring keys derived with HKDF
Link secret32 random bytes, base64url, carried only in the URL fragment: #a=<grant-id>.<secret>
DecryptionIn the reader's browser with WebCrypto. The fragment is removed from the address bar right away with history.replaceState
Private URLsOpaque tokens (/s/<token>/), so note names and paths aren't exposed
Expiry and revokeGrants carry expiresAt. Revoking deletes the grant. Both take effect at the next deploy (nightly at the latest)

Grant record (private/access.json)

FieldMeaning
idGrant identifier (appears in the link fragment)
kindlink (first version). code is reserved for typed access codes later

createdAt, expiresAtISO 8601 timestamps with offset
secretSecret material. It exists only in the private repository and never appears in the public repository, logs, or telemetry

Threat model

Protects against

  • Crawlers, search engines, and anyone browsing the public site or repository
  • Wrong, expired, or revoked links (after the next deploy)
  • A grant for one note unlocking a different note
  • Private plaintext slipping into the Pages artifact (the leak check)

Does not protect against

  • Recipients forwarding the link or saving the decrypted text
  • Content already downloaded or cached before revoke or expiry
  • Metadata: that sealed files exist, their sizes, and when they change
  • Script injection on the site's origin, which could read keys in the browser (mitigated by CSP and sanitizing)
  • Material that must stay confidential under contract or policy. Don't put that kind of content on public hosting, even encrypted
