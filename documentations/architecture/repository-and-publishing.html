Architecture

Repository and publishing

Each user owns their whole instance: one repository with their public notes, a private submodule, and a Deploy app workflow that publishes the app to their own GitHub Pages, with private notes only as ciphertext.

TL;DR

Every user's Focus Notes is their own, isolated instance in their own GitHub account (D-38, D-84, D-87). An instance is one repository (the notes repository): public notes in notes/, a private repository linked at private/ as a Git submodule (private notes in its notes/, synced settings in .focus-notes/, grants in access.json), the same pattern as the personal-site project, and a Deploy app workflow. People who just want to use Focus Notes copy the small template repository (not the source repository) to make their instance; its workflow deploys the released web app bundle at a pinned version, checked by SHA-256 and attestation (D-48). The project repository is the owner's own instance and builds the app from source. Only the desktop app writes to either repository; the browser only reads the deployed site (D-90). On each push, the workflow checks out both repositories (the private one with a read-only deploy key), publishes the app and public notes, seals the vault and shared notes with AES-256-GCM, checks that no plaintext leaked, and deploys to that instance's own GitHub Pages site. The vault is a share grant with an audience of one: every private note, opened in the browser by the owner's passphrase. Ciphertext exists only in the deployed site, never in Git history, with fresh keys every build. Nothing runs on a server.

A user's instance repository tracks only the submodule pointer, never the private files. This follows the personal-site setup, where .gitmodules declares the private repository with branch = main. The desktop app's Set up my instance copies the template, makes the private repository, installs the read-only deploy key and the sealed PRIVATE_CONTENT_KEY secret, clones and links them, records the vault's grant, turns on Pages, and pushes, each step retryable on its own (FRE-08, D-98, Creating a workspace). The project never sees either repository.

Nothing hosted, nothing registered

Each instance runs on the user's GitHub account alone: their repositories, their Actions, their Pages site, and their own credentials. There's no OAuth app, client ID, server, or telemetry run by the project (D-21). The only hosting is GitHub Pages (each instance's own site) and GitHub Releases. The owner's Pages site is the owner's own app: until a browser unlocks the vault with the owner's passphrase, it shows only public notes, the browser's own notes, and Use this app for yourself (D-87, D-90).

Working with the submodule

  1. Clone

    git clone --recurse-submodules, or run git submodule update --init after cloning. Without access to the private repository the submodule stays empty and the app still builds and runs with public content only (PKG-04).

  2. Track main

    The app keeps private/ checked out on main and pulls and pushes it as a repository of its own (D-47). It sets push.recurseSubmodules=check in the notes repository when it opens a workspace with private/ (D-97) but leaves submodule.recurse off. The pointer moves only after private pushes, batched (D-07), so it can trail main, and a recursive pull would reset private/ to an older commit and hide recent private notes. People using the terminal get the same advice in the workspace's AGENTS.md and README: pull private/ on its own.

  3. Commit private first

    Any change to private notes is committed and pushed to the private repository before the notes repository's pointer is updated. A pointer must never reference a private commit that hasn't been pushed.

How the desktop app writes

The desktop app is the only client that writes to either repository (D-90). It works on a local clone and runs the user's own git: commit in private/ and push, then commit and push the notes repository, moving the pointer to the pushed private commit (D-07). push.recurseSubmodules=check stops a public push whose pointer refers to an unpushed private commit. Details are in Desktop and Git.

What the browser reads

The web app (MW, D-80) never signs in to GitHub and never calls its API (D-90). Everything it shows of the instance comes from the deployed site, on its own origin:

  1. The site manifest, /focus-notes.json: the current build ID, where the public index is, and whether the site has a vault.
  2. Public notes: /notes/index.json lists them, and each one is served as Markdown at /notes/<path>. They open read-only.
  3. Private notes, after Unlock: the vault's keyring at /_access/<build>/vault.json, the sealed manifest it opens, and each sealed note when it's opened, all decrypted in the browser and shown read-only (The vault).

Notes written in the browser stay in that browser's IndexedDB until they're exported and imported by the desktop app (Web app).

The deploy seals private/ at the pointer, so the pointer decides how current the vault is. Since every private note is in the vault, every private change is publishing-relevant: D-07 (amended by D-90) has the desktop app move the pointer after each private push, batched so a writing session makes at most one public commit every few minutes. As built (D-97), the pointer moves to a pushed private commit at once the first time in a session, then at most once every 5 minutes (riding along in any notes commit that's happening anyway), and on quit whatever the gap. The browser's vault follows within one deploy.

Deploy pipeline

Triggers
Push to main, manual dispatch, and a nightly schedule (17 3 * * *) so share-link expiry takes effect without a push, in both the project's and the template's workflow. Only the default branch deploys, and only there is private/ checked out (github.event.repository.default_branch; scheduled runs always run on it). A final after-deploy job runs whatever the deploy's result: it deletes the run's github-pages artifact, which holds the build's keyrings and sealed files and would otherwise stay downloadable from the run after a later deploy replaced them (the upload also keeps it a day at most), and on a scheduled run it then applies the inactive-repository rule (Expiry, withdrawal, and deploys), so a quiet repository still deploys before the run fails (WP-5.2, D-117).
Private checkout
The Actions secret PRIVATE_CONTENT_KEY holds an SSH deploy key whose public half is installed read-only on the private repository. The checkout runs after every third-party step (install, tokens, the Vite build, the bundle's download and checks, and configure-pages), right before the publish step; the only action after it is the artifact upload, once private/ is gone (pinned by tools/test/deploy-workflows.test.mjs for both workflows): the workflow rewrites the submodule URL to SSH, runs git submodule update --init --depth 1 private, and checks that private/access.json exists (refusing to deploy a half-configured site). The key is removed by a shell trap however the step ends, checkouts use persist-credentials: false, and private/ is deleted straight after publishing. Without the secret it skips this step, and the site has public notes only and no vault.
Build logs that could reveal private note names are sent to a runner-local file instead of the public Actions log.
App and public notes
In an instance made from the template, the Deploy app workflow downloads the released web app bundle at the version it pins, focus-notes-web-<version>.tgz from the project's release v<version>, holding app/ (the web app, copied to the site's root) and publish/cli.mjs (packages/seal's command line, bundled), and checks it against a SHA-256 recorded in the workflow file (FOCUS_NOTES_VERSION, FOCUS_NOTES_SHA256) and against the release's GitHub artifact attestation (gh attestation verify --repo prabinpebam/focus-notes) before unpacking it. Until a release has a bundle, the template pins a marked placeholder version and the workflow refuses to run (D-98). Every action in the workflow is pinned by full commit SHA (not a movable tag), as GitHub's security hardening guide recommends, because the workflow runs with the user's PRIVATE_CONTENT_KEY (D-48, SEC-05). The project repository builds the same app from source instead. Either way the app goes at the site's root, every note in notes/ is published with it at /notes/<path> with an index, /notes/index.json, and the site manifest /focus-notes.json records the build. Each public note is also rendered to a static, read-only page at /n/<path>/ (WP-5.1, D-114): the publisher runs the page renderer (--reader apps/web/dist-reader, built with the web app) on the Markdown, through the bridge, the reader view document, and the UI runtime, and copies the pages' stylesheet and fonts into assets/; --site-url, from configure-pages, gives each page its canonical link. Pages have no script, follow the reader's light or dark preference, and are part of the leak check like every other file. Updates reach users only as a pull request in their own repository that moves the pinned version (Dependabot, or the app's Update publishing button), which they merge themselves (DST-06).
Seal
Seals the owner's grant (the vault: every private note) and each active share grant. For each grant it writes a keyring into _access/<build>/, and a sealed manifest and the sealed notes and their media into _sealed/<build>/, with fresh keys every build. Each note is sealed once per build, with its own key, and listed by every manifest that opens it; a note no active grant opens isn't sealed at all (D-117). The publisher is packages/seal (the format, the sealer, and the reader, on Web Crypto only, so the same code runs in Node and in browsers), run by the project's workflow as node packages/seal/src/cli.ts publish --site _site --notes notes --private private --owner <owner>, and by a template instance's as node publish/cli.mjs publish … from the bundle. Without private/, or without private/access.json, it publishes public notes only and writes "vault": false; the project's workflow refuses a private checkout without access.json, while a template instance's deploys public notes only, because the setup's Skip for now leaves the vault for later (D-98).
Verify
The leak check (SEC-06), run by the publisher before upload: it fails the deploy if any private note's path of 12 characters or more, or any line of private text of 24 characters or more, appears in any text file of the site output. So does any grant's secret, of any length and whether the grant is in force or not: a link's secret, a passcode, or the vault's derived key, as stored, in Unicode NFC and NFD, base64url written as standard base64, URI-encoded, and JSON-escaped; and any share audience's name of 6 characters or more (as written, in NFC, or normalized as the lookup does it) in what the publisher generates for sealing (_access/, _sealed/, and focus-notes.json). Those files are read as JSON and only their keys and plain fields are searched for names, never the ciphertext and random fields (data, iv, salt, nameSalt), where a name could turn up by chance. Names aren't searched in public notes, their index, or their pages, which may mention the person (WP-5.2, D-117). Shorter names, such as Todo.md, are too common to test without failing on the app's own files. It never prints the matched text, because the Actions log is public: only the file and whether a path, text, secret, or name matched.
Deploy
Uploads the verified artifact to the user's own GitHub Pages site. Only the default branch deploys. Whatever the deploy's result, the after-deploy job then deletes the run's artifact, so a failed deploy needs Re-run all jobs, which builds a new artifact; Re-run failed jobs would find the artifact gone.

Sealing and share links

This follows the personal-site access design (grants, keyrings, fresh keys every build, and a nightly deploy), adapted to Focus Notes: an audience is just a name, and it can have a magic link, a passcode, or both (D-41). The owner's own access to private notes in the browser uses the same scheme: the vault is a built-in grant for "You" (D-90). The experience is in Sharing and visibility.

Grant record (private/access.json)

The private repository's history is the audit trail: every grant's creation, change, withdrawal, and deletion is a commit. The JSON Schema is published with the product (AGT-08).

Sealed files and lookup

  • Every build has a random build ID. Sealed files live under _sealed/<build>/ and keyrings under _access/<build>/, so a deploy never overwrites a file that a cached page still needs.
  • Link keyrings are found by grant ID: _access/<build>/l/<id>.json. The reader accepts only IDs matching ^[A-Za-z0-9_-]{8,64}$, so a link can't name another file, and only a keyring that names the grant the link asked for.
  • Passcode keyrings are found by name: _access/<build>/p/<lookup>.json, where lookup is PBKDF2-HMAC-SHA256 over the normalized name with the workspace salt's bytes and 50,000 iterations, 16 bytes as 32 lowercase hex characters, so each guessed name costs real work. The name is normalized (Unicode NFKC, trimmed, case-folded as ECMAScript's upper case then lower case, so Straße and STRASSE match). The workspace salt (nameSalt in access.json, 16 to 64 bytes as base64url text) is public and stable, so remembered keys keep working across builds; the publisher copies it into the site manifest whenever there's an access.json, and uses a fresh salt for the build if access.json has none (D-117). Two active audiences whose names normalize the same fail the deploy, without the error quoting either name. The lookup only finds a keyring. Opening it still needs the passcode. It can't hide whether a guessed name has a share: anyone with the site's nameSalt can compute a name's lookup and see whether that file exists, at 50,000 iterations a guess. For the few minutes before after-deploy deletes it, the run's Pages artifact lists every _access keyring file at once, so anyone who downloads it can guess names offline against that list, without asking the site about each one. Putting a random keyring ID in the invite instead of a name lookup would remove that, and is proposed to the owner in D-117. The vault's keyring has a fixed name, _access/<build>/vault.json.
  • Each share keyring has its own salt, HKDF-SHA256 of the grant's salt with the info focus-notes/salt/v1|link or |passcode, so a grant's two keyrings can't be matched up by their headers. The vault's keyring uses the owner's grant's salt, which its stored key was derived with.
  • A keyring is a small JSON envelope with its derivation in clear (kdf, iterations, salt, iv), and the header is authenticated as additional data. Decrypted, it holds the grant ID, the expiry, and the key ID and key of the grant's sealed manifest, not the note keys themselves, so keyrings stay small however much a grant opens. The browser accepts only pbkdf2-sha256 at exactly 600,000 iterations (the vault and passcode keyrings) or hkdf-sha256 (link keyrings, which have no iterations), each only where it's expected, a 16-byte salt, a 12-byte IV, and files under 64 KB, so the format can't be downgraded or used to exhaust the browser.
  • A sealed manifest lists what the grant opens: each note's per-build key ID and key, its path relative to the shared scope, its title, and when it changed. A grant's scope names notes by ID (front matter id) or path, and folders by prefix, which include notes added later. Relative to the scope means a shared folder keeps its own name and what's inside it (Work/Projects/drafts/Plan.md shared as the folder Work/Projects/drafts/ reads drafts/Plan.md), a shared note is just its file name, and two that would read the same get (2) before the extension. The vault keeps whole paths. Only the owner's grant may have scope.all; on a share grant it's ignored, so an audience opens only the notes and folders it names (D-117). Paths and titles are inside the ciphertext, so file names stay opaque on the site.
  • Sealed manifests and notes use AES-256-GCM with a random 96-bit IV. The additional data binds each file to its build and key ID (focus-notes/manifest/v1|<build>|<kid>, focus-notes/note/v1|<build>|<kid>), so swapped or stale files fail the authentication tag.
  • A sealed page's <title> is "Private note". It has no description, and adds noindex, nofollow and referrer: same-origin.

Expiry, withdrawal, and deploys

  • Fresh keys every build. Keyrings are written only for grants that are neither expired nor withdrawn, so ended grants open nothing on the live site.
  • Publishing on change. Creating, extending, or withdrawing a grant commits to the private repository, moves the pointer (D-07), and the push starts a deploy. The change takes effect in about 15 minutes (the deploy, plus up to 10 minutes of browser caching on GitHub Pages).
  • Nightly deploy. A scheduled run applies expiry dates. GitHub may start scheduled runs late. Keyrings also carry the expiry, and the reader page refuses expired ones itself.
  • Inactive-repository rule. GitHub turns off scheduled workflows in public repositories after 60 days without activity. As in personal-site, when the last commit is 50 days old the nightly run fails on purpose with a message saying so (GitHub emails the owner about the failed run), and the app shows a reminder (any commit resets the clock). Both workflows have the check, in the after-deploy job, so the night's deploy still happens first (WP-5.2); the app's reminder isn't built yet.
  • Generic errors. The share reader (SiteReader.openLink and openPasscode in packages/seal) turns every failure, a missing, withdrawn, or expired grant, a wrong name, passcode, or link, or a damaged file, into one error, so the reader's answer never says whether a note or an audience exists (SHR-06). The site's files can: whether a guessed name's passcode keyring is there (see the lookup above).

The protections and limits are listed in the threat model below and in Security and privacy.

The vault

The vault is a share grant with an audience of one (D-90): a built-in grant for the owner whose scope is every private note and whose passcode is the vault passphrase. The desktop app's setup asks for the passphrase and stores only its derived key in private/access.json (FRE-08, as built in WP-3.1). From a terminal, node packages/seal/src/cli.ts vault-init --private private creates the same grant with the same code (withVaultGrant in packages/seal): it reads the passphrase from standard input (never from arguments), refuses weak ones, and writes only the derived key. The instance's own Deploy app workflow, which already checks out private/ with the read-only deploy key, seals it on every deploy with fresh keys. Ciphertext exists only in the deployed Pages artifact, never in Git history. Paths stay readable in the private repository and are opaque on the site. A browser opens it with the passphrase, read-only (Web app → Unlocking private notes).

  1. Site manifest

    The browser reads /focus-notes.json for the current build ID and whether there's a vault.

  2. Keyring

    It reads /_access/<build>/vault.json, checks it strictly, derives the key from the passphrase (or uses a remembered key), and decrypts the manifest's key ID and key.

  3. Sealed manifest

    It reads and decrypts /_sealed/<build>/<kid>.json: the private notes' paths, titles, dates, and note keys.

  4. Sealed note

    When a note is opened, it reads and decrypts that note's /_sealed/<build>/<kid>.json and shows the Markdown read-only.

Remembering and locking

  • By default the derived key lives only in memory, and the vault locks when the page closes or reloads.
  • Remember on this browser imports the derived key as a non-extractable AES-GCM CryptoKey and stores it in IndexedDB with its salt. It opens every later build's keyring until the passphrase changes. Every site on the same <user>.github.io origin can reach that storage, so the app warns again next to the option, on top of the warning the unlock dialog always shows (SEC-08).
  • Lock drops the key and the decrypted notes from memory. Forget this browser also deletes the remembered key.
  • Changing the passphrase (in the desktop app) writes a new salt and key to the owner's grant, so remembered keys stop opening the vault after the next deploy.
  • A forgotten passphrase can't be recovered. The notes stay in the private repository, readable in the desktop app, which can set a new one.
  • No private path is stored. The app's lastNotePath (in appState) is saved only for the browser's own notes and public notes, so a reload never reopens a private note or leaves its name in IndexedDB.

Hardening

  • The shared origin is the main limit. Every Pages site of one user is the origin <user>.github.io, so any page there can script this one: while the vault is open it could capture the passphrase as it's typed or read decrypted notes, and it could use a remembered key. So the unlock dialog always shows the shared-origin warning, not only next to Remember on this browser. A custom domain for the instance's site is the real fix.
  • Private content enters the build late. The Deploy app workflow checks out private/ only after every third-party build step, right before publishing, and deletes it straight after; the deploy key is removed by a shell trap, and checkouts use persist-credentials: false (Deploy pipeline).
  • The publisher reveals nothing. It skips symbolic links in notes/ and private/, and its errors never quote private file names or access.json content.
  • The browser reads strictly. It accepts the public index only at notes/index.json, and caps sizes: the site manifest at 64 KB, the public index at 8 MB, each public or sealed note at 8 MB, the sealed manifest at 4 MB, and keyrings at 64 KB. Export bundles over 64 MB or 20,000 notes are refused unread.
  • vault-init reads the passphrase from standard input and doesn't echo it when typed at a terminal.

Threat model

Protects against

  • Crawlers, search engines, and anyone browsing the public site or repository
  • Anyone without the vault passphrase reading the owner's private notes on the site
  • Wrong names or passcodes, and expired or withdrawn audiences (after the next deploy)
  • An audience for one note or folder opening anything else
  • Private plaintext or file names slipping into the Pages artifact (the leak check)

Does not protect against

  • Readers forwarding the link or passcode, or saving the decrypted text
  • Content already downloaded or cached before revoke or expiry
  • Metadata: that the site has a vault, that sealed files exist, their sizes, and when deploys happen
  • Whether a guessed audience name has a share: its passcode keyring's file is there or isn't (each guess costs 50,000 PBKDF2 iterations; D-117 proposes a random keyring ID in the invite instead), and offline against the run's Pages artifact, which lists every keyring file, for the minutes before after-deploy deletes it
  • The run's Pages artifact, downloadable from the Actions run for the minutes between its upload and after-deploy deleting it (a day at most if the deletion fails); it holds only what the site serves, but all at once, including the full list of _access keyring files, which allows offline name guessing in those minutes until D-117 (12), a random keyring ID, is decided
  • A forgotten vault passphrase: it can't be recovered (the notes stay in the private repository)
  • Script injection on the site's origin, or another page on the same <user>.github.io origin, which can script this one: capture the passphrase as it's typed, read decrypted notes while unlocked, or use a remembered vault key. CSP, sanitizing, opt-in remembering, and an always-shown warning reduce it; only a custom domain removes it
  • Material that must stay confidential under contract or policy. Don't put that kind of content on public hosting, even encrypted
