Architecture

Repository and publishing

Each user owns their whole setup: a public notes repository, a private submodule, and their own GitHub Pages build that never publishes private plaintext.

TL;DR

Every user's Focus Notes is their own, isolated instance in their own GitHub account (D-38). Their public notes repository (created from the Focus Notes template) holds public notes and the publish workflow. Their private notes live in a separate private repository mounted as a Git submodule at private/, the same pattern as the personal-site project. The product repository only provides the app's source, its releases, and the template. Nothing is hosted for users. GitHub Actions in the user's repository checks out both of their repositories (the private one with a read-only deploy key), builds the app and public note pages, seals any privately shared notes with AES-256-GCM, checks that no plaintext leaked, and deploys to their GitHub Pages site. Readers of shared private notes decrypt them in their own browser using the key in the link's #fragment.

A user's notes repository tracks only the submodule pointer, never the private files. This follows the personal-site setup, where .gitmodules declares the private repository with branch = main. Both user repositories are created by the app on the user's computer during first run (see Creating a workspace). The project never sees them.

Nothing hosted, nothing registered

Each instance runs on the user's GitHub account alone: their repositories, their Actions, their Pages site, and their own credentials in Git's credential helper. There's no OAuth app, client ID, server, or telemetry run by the project (D-21). The only shared things are public files on GitHub: the template, the reusable workflow, and the release downloads.

Working with the submodule

  1. Clone

    git clone --recurse-submodules, or run git submodule update --init after cloning. Without access to the private repository the submodule stays empty and the app still builds and runs with public content only (PKG-04).

  2. Track main

    The app keeps private/ checked out on main and pulls and pushes it as a repository of its own (D-47). It sets push.recurseSubmodules=check but leaves submodule.recurse off. The pointer only moves for publishing (D-07), so a recursive pull would reset private/ to an older commit and hide recent private notes. People using the terminal get the same advice in the workspace's AGENTS.md and README: pull private/ on its own.

  3. Commit private first

    Any change to private notes is committed and pushed to the private repository before the notes repository's pointer is updated. A pointer must never reference a private commit that hasn't been pushed.

How the desktop app writes

The desktop app works on a local clone and runs the user's own git: commit in private/ and push, then commit and push the notes repository (moving the pointer only as D-07 describes). push.recurseSubmodules=check stops a public push whose pointer refers to an unpushed private commit. Details are in Desktop and Git.

How the web app writes

The web app (MW, the primary client, D-80) can't run Git, so the GitHub API adapter does the same thing through the REST API:

  1. Public note change: one commit to the notes repository (contents API for single files, git trees and commits API for batched moves).
  2. Private note change: a commit to the private repository, then a commit to the notes repository that updates the private gitlink (tree entry mode 160000) to the new private commit SHA.
  3. Visibility change: add the note to the target repository, delete it from the source repository, then update the pointer. Private side first, as always.

Bumping the pointer on every private save would trigger a public deploy (and a public commit) for every keystroke pause. Proposed (D-07): update the pointer only when the private change affects publishing (share grants or shared notes), plus once a day. Ordinary private edits stay in the private repository.

Deploy pipeline

Triggers
Push to main, manual dispatch, and a nightly schedule so share-link expiry takes effect without a push.
Private checkout
The Actions secret PRIVATE_CONTENT_KEY holds an SSH deploy key whose public half is installed read-only on the private repository. The workflow rewrites the submodule URL to SSH, runs git submodule update --init --depth 1 private, checks that private/access.json exists (refusing to deploy a half-configured site), then deletes the key from the runner.
Build logs that could reveal private note names are sent to a runner-local file instead of the public Actions log.
Build
Calls the Focus Notes reusable publish workflow, pinned by full commit SHA (not a movable tag), as GitHub's security hardening guide recommends, because the workflow runs with the user's PRIVATE_CONTENT_KEY. It downloads the matching release's static reader bundle from GitHub Releases, checks it against a SHA-256 recorded in the workflow file and against the release's GitHub artifact attestation, and renders every note in content/ to a static page at /n/<path>/. Updates reach users only as a pull request in their own repository (Dependabot, or the app's Update publishing button) that they merge themselves (D-48).
Seal
For each active grant, encrypts the granted notes and their media into _sealed/<build>/ and writes the grant keyrings into _access/<build>/.
Verify
A leak check scans the output for any private text or file names and fails the deploy if it finds any.
Deploy
Uploads the verified artifact to the user's own GitHub Pages site. Only main deploys.

Sealing and share links

This follows the personal-site access design (grants, keyrings, fresh keys every build, and a nightly deploy), adapted to Focus Notes: an audience is just a name, and it can have a magic link, a passcode, or both (D-41). The experience is in Sharing and visibility.

Grant record (private/access.json)

FieldMeaning
idRandom and opaque (g plus 8 base32 characters). Appears in a magic link's fragment.
nameThe audience: a person or group. The only detail recorded about who it's for. Unique among active grants.
linkPresent if the audience has a magic link: { "secret": "<32 random bytes, base64url>" }.
passcodePresent if it has a passcode: { "value": "…", "generated": true }. Kept so the invite can be copied again. Never published.
salt16 random bytes. Published in the keyring header (it isn't secret).
scope{ "notes": ["<note id>"], "folders": ["drafts/"] }. A folder includes notes added later.
createdAt, expiresAt, revokedAtISO 8601 with time zone. expiresAt is optional. revokedAt is set on withdraw, and the record stays.

The private repository's history is the audit trail: every grant's creation, change, withdrawal, and deletion is a commit. The JSON Schema is published with the product (AGT-08).

Sealed files and lookup

  • Every build has a random build ID. Sealed files live under _sealed/<build>/ and keyrings under _access/<build>/, so a deploy never overwrites a file that a cached page still needs.
  • Link keyrings are found by grant ID: _access/<build>/l/<id>.json.
  • Passcode keyrings are found by name: _access/<build>/p/<lookup>.json, where lookup is the first 16 bytes of SHA-256 over focus-notes/name/v1|<workspace salt>|<name>. The name is normalized (Unicode NFKC, trimmed, case-folded). The workspace salt is public and stable, so remembered keys keep working across builds. The lookup only finds a keyring. Opening it still needs the passcode.
  • A keyring is a small JSON envelope with its derivation in clear (kdf, iterations, salt, iv), and the header is authenticated as additional data. Decrypted, it holds the grant ID, the expiry, and the note keys it opens (by per-build key IDs, never note IDs). The browser accepts only pbkdf2-sha256 at exactly 600,000 iterations or hkdf-sha256, a 16-byte salt, a 12-byte IV, and files under 64 KB, so the format can't be downgraded or used to exhaust the browser.
  • Sealed notes use AES-256-GCM with a random 96-bit IV. The additional data binds each file to its build and key ID (focus-notes/note/v1|<build>|<kid>), so swapped or stale files fail the authentication tag.
  • A sealed page's <title> is "Private note". It has no description, and adds noindex, nofollow and referrer: same-origin.

Expiry, withdrawal, and deploys

  • Fresh keys every build. Keyrings are written only for grants that are neither expired nor withdrawn, so ended grants open nothing on the live site.
  • Publishing on change. Creating, extending, or withdrawing a grant commits to the private repository, moves the pointer (D-07), and the push starts a deploy. The change takes effect in about 15 minutes (the deploy, plus up to 10 minutes of browser caching on GitHub Pages).
  • Nightly deploy. A scheduled run applies expiry dates. GitHub may start scheduled runs late. Keyrings also carry the expiry, and the reader page refuses expired ones itself.
  • Inactive-repository rule. GitHub turns off scheduled workflows in public repositories after 60 days without activity. As in personal-site, when the last commit is 50 days old the nightly run fails on purpose with a message saying so, and the app shows a reminder (any commit resets the clock).

The protections and limits are listed in the threat model below and in Security and privacy.

Threat model

Protects against

  • Crawlers, search engines, and anyone browsing the public site or repository
  • Wrong names or passcodes, and expired or withdrawn audiences (after the next deploy)
  • An audience for one note or folder opening anything else
  • Private plaintext slipping into the Pages artifact (the leak check)

Does not protect against

  • Readers forwarding the link or passcode, or saving the decrypted text
  • Content already downloaded or cached before revoke or expiry
  • Metadata: that sealed files exist, their sizes, and when they change
  • Script injection on the site's origin, which could read keys in the browser (mitigated by CSP and sanitizing)
  • Material that must stay confidential under contract or policy. Don't put that kind of content on public hosting, even encrypted
