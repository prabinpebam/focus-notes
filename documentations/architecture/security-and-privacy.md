# Security and privacy

What Focus Notes protects, from whom, and how. It also covers what's stored where, and the privacy commitments the product makes.

> [!NOTE]
> **TL;DR.** The product runs **no servers and collects nothing**: no telemetry, no analytics, and no third-party requests in the app, the users' sites, or these docs (PRV-01). Each user's data lives on their computer, in their browser, and in their own GitHub repositories. Credentials live only in Git's credential helper, used by the desktop app; **the browser holds no GitHub credential at all** and never writes to GitHub (D-90). The main risks are **leaking private notes** (through publishing, an XSS bug, an agent, or a malicious dependency), **weak passcodes or a weak vault passphrase** facing offline guessing, the **shared `github.io` origin** that every Pages site of a user shares, and the **supply chain** behind code that runs with users' secrets. Controls follow established checklists: OWASP ASVS Level 2, Electron's security checklist, GitHub's Actions hardening guide, and OWASP's guidance on LLM prompt injection for agents.

## What we protect

| Asset | Where it lives | Worst case |
| --- | --- | --- |
| Private and shared notes | `private/` on disk, the private repository, sealed copies on Pages (the vault and share grants) | Published or read by the wrong person |
| GitHub credential (desktop only) | Git's credential helper (OS keychain or Credential Manager) | Account takeover of repositories |
| Share secrets and passcodes | `private/access.json` (private repository) | Shared notes opened by people who weren't given access |
| The vault passphrase | Only in the owner's head. `private/access.json` holds its derived key; a browser holds that key only with *Remember on this browser* (a non-extractable `CryptoKey`) | Every private note readable from the public site |
| Share-link deploy key | The notes repository's Actions secret | Private repository read by a malicious workflow |
| Notes written in a browser | That browser's IndexedDB, on the site's origin | Lost when the site's data is cleared, or read by a script on the same origin |
| The writer's identity | Commit author (the noreply address by default) | Personal email exposed in public history |

## Threats and controls

| Threat | Controls | Requirements |
| --- | --- | --- |
| **Malicious content in a note or pasted HTML** (XSS in the editor or on public pages) | Raw HTML in a note is shown as text: it's kept verbatim as a read-only block and never parsed as markup. Pasted or dropped HTML is sanitized with an allow-list (DOMPurify) before anything parses it: no scripts, event handlers, frames, SVG, forms, or image sources, and styles only for bold, italic, strikethrough, and Word's lists. The sanitized HTML is read in an inert document and converted to Markdown, so only the editor's own blocks and marks come in. Only safe link schemes (`https`, `http`, `mailto`, relative) are allowed: unsafe links in a paste become text, and in a note they render without an address while the file keeps them as written. The public renderer sanitizes with an allow-list. A strict CSP everywhere, with no inline scripts, and **Trusted Types** in both shells: `require-trusted-types-for 'script'` with only the `default`, `dompurify`, and `search-worker` policies. The app writes no HTML itself; the `default` policy passes text without markup as it is (a live region clearing itself, the Markdown parser decoding `&copy;`) and sanitizes anything with markup, and nothing may create scripts (D-93). The one script URL is the search index's worker: `search-worker` passes only the worker file the build made, on the app's own origin, and refuses any other address (D-107). | SEC-02 |
| **Compromised renderer gets system access** (Electron) | `contextIsolation`, `sandbox`, no `nodeIntegration`, a narrow typed preload bridge with validated arguments. Navigation, new windows, and `webview` are denied. A note's links open only through the bridge (`link:open`), which the main process re-checks for `http`, `https`, or `mailto` before handing them to the default browser; the clipboard bridge (`clipboard:write`) writes text and never reads it (D-91). Share audiences (D-134) go through `access:load`, `access:apply`, `access:reveal`, and `access:copy`: the main process alone reads and writes `private/access.json`, checks each change field by field (`parseAccessChange`) and again with the publisher's `validateAccess`, and makes every secret, generated passcodes included; the listing the window gets has no link secret, passcode, or salt, and never the vault's key. A compromised window can still ask for one audience's link or passcode (`access:reveal`) or put it on the clipboard, and can make, change, or withdraw audiences, as the owner can; it can't read the vault's key, mark its own passcode as generated, or write anything but a valid access file. Secrets copied by `access:copy` are cleared from the clipboard after 90 seconds if it still holds them; Windows clipboard history and its cloud sync may keep a copy, because Electron can't mark text as excluded from them. The Files panel's file-system items (D-192) go through `workspace:revealItem` and `workspace:copyItems`: the main process accepts only paths inside a workspace root, as the file system resolves them (no control characters, dot folders, symbolic links or short names leading elsewhere), shows them with `shell.showItemInFolder`, and puts them on the clipboard as files through the system's own tool, started by absolute path (PowerShell on Windows, `osascript` on macOS) with the paths in an environment variable, never in the command. A compromised window could put any note, private ones included, on the clipboard as a file or as text (`clipboard:write` takes a note's length), as the person can; the same clipboard history caveat applies to a note's text. Permission requests are denied by default. No remote content is loaded. Electron fuses: `RunAsNode` off, `EnableNodeOptionsEnvironmentVariable` off, `EnableNodeCliInspectArguments` off, `OnlyLoadAppFromAsar` on, embedded ASAR integrity validation on, cookie encryption on (D-116). | SEC-01, SHR-05 |
| **Notes pushed to a public template repository** (D-157: before D-147, *We found your notes* listed the public template, and opening it committed and pushed the owner's notes there) | A template is never someone's notes. One guard (`apps/desktop/src/main/git/template-guard.ts`) knows the Focus Notes template by name, in any letter case, without the network, and asks GitHub's `is_template` for any other repository, keeping the answer for the session. It's asked at every way in (listing, opening or downloading from GitHub, every push URL of a local folder's `origin`, switching workspace, setup's parts) and **before every push**, in saving and in setup, checking **every push URL** of the remote, and again before the retry after a rejected push. A template's push is refused, the commits stay on this computer, and the person is told plainly, with *Run setup again*. The known template's name is refused **anywhere in a URL** (any case, any owner, host, or SSH alias). A remote it **can't read** as owner/name on GitHub or an SSH alias for it (`git@alias:o/n`, `ssh://…:443/o/n`, `www.github.com`) is refused too ("Focus Notes can't tell which repository this workspace saves to"). **Where it fails open** (residual risk, accepted so saving never stops on a network hiccup): GitHub's answer is unknown when signed out, offline the first time a repository is checked, a 404 (not visible to this account), a 10 s timeout, or any other error; then the last good answer is used, and a repository never known as a template saves as normal. A repository made a template mid-session is caught within 10 minutes (the cache's age), or at the next launch. Another web host (not GitHub) and a folder on this computer aren't checked with GitHub; a non-GitHub address that redirects to GitHub isn't followed. The known template is refused whatever GitHub says. | SEC-06 |
| **Private notes published by mistake** | Private by default. Moving to Public needs confirmation. The pipeline seals the vault and shared notes and **fails the deploy if any private note's path of 12 characters or more, or any line of private text of 24 characters or more, appears** in the output, or **any grant's secret** (a link secret, a passcode, or the vault's key, also in NFC, NFD, standard base64, URI-encoded, and JSON-escaped forms) or **share audience name** of 6 characters or more (also normalized) does in the keyrings, sealed files, or site manifest, outside their ciphertext fields (public notes may mention the person) (the leak check). It reports only the file and whether a path, text, secret, or name matched, never the text, because the Actions log is public. The publisher skips symbolic links, and its errors never quote private file names or `access.json` content. | SEC-06 |
| **Old keyrings in the Pages artifact** (each run's artifact holds the build's keyrings and sealed files, which a later deploy would otherwise leave downloadable) | The Deploy app workflow's last job deletes the run's github-pages artifact after the deploy, and the upload keeps it a day at most if that fails. It's downloadable from the run for the minutes in between, and holds only what the site serves, but **it lists every `_access` keyring file at once, so in those minutes anyone who downloads it can guess audience names offline** against that list, until a random keyring ID (D-117 (12)) is decided. Because the artifact is gone, a failed deploy needs **Re-run all jobs**, not Re-run failed jobs (D-117) | SHR-11 |
| **Guessing share passcodes offline** | Generated passcodes of about 52 bits, a strength check for every passcode in force, generated or not, that fails the deploy (without quoting the passcode), PBKDF2-SHA256 at 600,000 iterations, a salt per keyring derived from the grant's, keyrings that refuse other parameters and name their role and grant in their additional data, and keyrings all the same size. The strength check is a rough estimate (accepted, as for SEC-08). A passcode keyring is found by PBKDF2-SHA256 of the name (50,000 iterations, the workspace's salt). The share reader's error is the same whatever went wrong, but **the site's files show whether a guessed name has a share** (its keyring is there or isn't); a random keyring ID in the invite instead would remove that, proposed in D-117 | SHR-07, SHR-11 |
| **Guessing the vault passphrase offline** (its keyring is published with every deploy) | The desktop setup requires a strong passphrase. PBKDF2-SHA256 at 600,000 iterations with a salt per grant, and the browser accepts no other parameters. Only the derived key is stored, in the private repository; the passphrase is never stored or sent. | SEC-08 |
| **Another page on the same `github.io` origin** (every Pages site of one user is the origin `<user>.github.io`: it shares the storage and can script this page, so it could capture the vault passphrase as it's typed, read decrypted notes while unlocked, or use a remembered key) | Only a **custom domain** for the instance's site removes this; the app reduces it. The browser holds no GitHub credential. The unlock dialog **always** shows the shared-origin warning. *Remember on this browser* is opt-in and stores only a non-extractable key; *Forget this browser* deletes it. No private note's path is stored: `lastNotePath` is kept only for the browser's own and public notes. | SEC-03, SEC-08 |
| **Forgotten vault passphrase** | Setup says plainly that it can't be recovered. The notes stay in the private repository, readable in the desktop app, which can set a new passphrase. | SEC-08 |
| **Forwarded links, or access that outlives its welcome** | Expiry by default, withdraw, and fresh keys every build. It's documented honestly that what was read can't be taken back. | SHR-08, SHR-11 |
| **Compromised dependency or release** | Lockfiles, Dependabot, CodeQL, secret scanning with push protection, an SBOM, GitHub artifact attestations, signed installers (DSK-07), and actions pinned by commit SHA | SEC-04, DSK-07 |
| **Compromised Deploy app workflow or web app bundle stealing users' private content** (the workflow runs with their deploy key) | Template instances pin every action by commit SHA and deploy the released web app bundle only at a pinned version, after checking its SHA-256 and attestation (D-48). Updates arrive as pull requests they merge themselves. The workflow checks out `private/` only after every third-party build step (install, tokens, the Vite build), right before publishing, deletes it straight after, uses `persist-credentials: false`, and removes the deploy key with a shell `trap`. | SEC-05 |
| **Stolen or lost laptop** | Notes on disk are protected by the OS account and disk encryption (recommended in the docs). Credentials are in the OS keychain. Signing out or removing the workspace deletes exactly what the data inventory lists for it (the recent note, setup's progress, the workspace's local data), and empties Chromium's caches. | PRV-02 |
| **Script injection in the web app** | Strict CSP (`connect-src 'self'` only) with Trusted Types, no third-party scripts, Markdown never rendered as raw HTML, and pasted HTML sanitized. There's no token to steal, and decrypted private notes exist only in memory while unlocked, the search index's copy included, which locking drops (D-107). | SEC-02, SEC-03 |
| **Hostile or oversized site files or import bundles** (exhausting the browser) | The browser accepts the public index only at `notes/index.json` and caps sizes: the site manifest 64 KB, the index 8 MB, each note 8 MB, a sealed manifest 4 MB, a keyring 64 KB. Import bundles over 64 MB or 20,000 notes are refused unread. | PKG-08, PKG-11 |
| **The vault passphrase seen while typed at a terminal** (`vault-init`, for people who set up in a terminal) | It's read from standard input, never from arguments, and not echoed. Weak passphrases are refused. | SEC-08 |
| **The token leaking from sign-in** (desktop, FRE-02, FRE-03) | Sign-in runs Git's own helpers (Git Credential Manager's `github login`, `gh auth login`) with fixed words as arguments and no shell; a pasted token is checked with `GET /user` from the main process and given to Git's helper only on standard input (`git credential approve`), and refused if no helper keeps it; the app never sets up the plaintext `store` helper. The renderer holds a pasted token only until it's sent, and never the token Git has. Journeys log every program the app starts and check that no token is in any argument (D-101). | SEC-03 |
| **The token, passphrase, or deploy key leaking from setup** (desktop, FRE-08) | The token is read from Git's credential helper (`git credential fill` for `github.com`, prompts off) each session and kept only in the setup engine's memory; it goes only to `api.github.com` (the main process's fetch refuses any other address and never follows a redirect), and never into a process argument, the environment, the log, or `setup.json`. The vault passphrase is passed to the main process only to run its step, refused if weak (`passphraseStrength`), and only its derived key is written. The deploy key is an Ed25519 pair made in memory: its public half is added **read-only**, its private half is sealed to the instance's Actions public key (libsodium's sealed box) before it leaves the app, and neither is written to disk. A key left by an interrupted setup is deleted and replaced (D-98). | SEC-03, SEC-08 |
| **Setup writing into the wrong place** (desktop) | It never uses a public repository as the private one, never uses a repository that isn't a Focus Notes workspace as the instance, never clones into a folder that has other files, and never links `private/` to a different repository than the one it made. Each refusal is a named problem the first run explains (D-98). | FRE-08 |
| **Script injection in the web app** | Strict CSP (`connect-src 'self'` only), no third-party scripts, Markdown never rendered as raw HTML. There's no token to steal, and decrypted private notes exist only in memory while unlocked, the search index's copy included, which locking drops (D-107). | SEC-02, SEC-03 |
| **Hostile or oversized site files or import bundles** (exhausting the browser) | The browser accepts the public index only at `notes/index.json` and caps sizes: the site manifest 64 KB, the index 8 MB, each note 8 MB, a sealed manifest 4 MB, a keyring 64 KB. Import bundles over 64 MB or 20,000 notes are refused unread. On the desktop only the main process reads a bundle, after the system's open dialog: the window gets a count, and the notes are written with names made safe, never over an existing file (D-99). | PKG-08, PKG-11, FRE-10 |
| **The vault passphrase seen while typed at a terminal** (`vault-init`, before the desktop setup exists) | It's read from standard input, never from arguments, and not echoed. Weak passphrases are refused. | SEC-08 |
| **Agent misuse or prompt injection** | See [Agents → Risks](agents.md#risks-specific-to-agents) | AGT-03, AGT-09 |
| **Private text or a secret in a diagnostic report** (pasted into a public issue) | The main process builds the report from facts (versions, counts, states, problem codes), never from note text, file names, or command output, and redacts it: the login, names, emails and repository names it knows, the workspace's and home folder's paths and everything after them, credentials and paths in addresses, tokens, secret-style values, private keys, emails, device codes, long encoded strings, other paths to the end of the line, and note file names, with its input capped and every pattern bounded. A saved report never goes into the workspace or the data folder. The window gets only a summary for the preview, through `diagnostics:preview`; `diagnostics:copy` and `diagnostics:save` take only the window's timings, which the main process checks again (the app's own measure names and numbers). The person sees what's included before copying. Nothing is sent unless the person presses *Send* in Send feedback with the report attached, and no address ever carries it (D-55, D-140, D-203) | QLT-04 |
| **Feedback posted somewhere else, or carrying more than the person wrote** (Send feedback, desktop) | The repository is a constant in the main process (`prabinpebam/focus-notes`); the window can't name another. `feedback:send` and `feedback:continue` accept only `{ kind, title, details, attachReport }` from the app's own page, checked strictly (exact keys, types, a title of 1 to 120 characters, details up to 5,000). The main process builds the issue: the person's words, one summary line (version, system, architecture), the redacted report only when attached, and a marker. **The person sees what's included before sending:** attached, the report's preview shows the exact redacted text, read-only, and the main process keeps that text from `feedback:preview` and posts or copies that same text, so the two can't differ; with none previewed, nothing attached goes. Only this preview gets the report's text in the window; it's going public anyway. At most 5 issues an hour from one run, and 5 s after a failure before another try. The token is read from Git's helper as setup's is and never leaves the main process; the window gets back only the issue's number and address, shown only when it's an issue of that repository, or a problem code. *Continue on GitHub* opens only `github.com/prabinpebam/focus-notes/issues/new`, never with the report in the address. The labelling workflow reads the issue's body in JavaScript only, never in a shell or a `${{ }}` expression, with `issues: write` alone (D-203) | QLT-07 |
| **Malicious theme or settings file** | Validated against schemas. Values only, never CSS or URLs. | UNSUP-THEME-01 |

Everything Focus Notes keeps, where, and what removes it. ## Privacy commitments

1. **No telemetry.** No usage analytics, crash reporting services, or error trackers, in any product surface (PRV-01). Problems are reported by the user: *Copy diagnostic report* puts a redacted report on the clipboard, and *Send feedback* posts an issue only when the person presses *Send*, as themselves, with the report only if they attach it, or opens a pre-filled GitHub issue they review there (QLT-04, QLT-07, D-203). Performance measurements stay on the computer too: the app's timings appear only in the diagnostic report, and published pages are measured in CI lab runs, never in readers' browsers (D-65).
2. **No third-party requests.** The app, the instances' sites (including the owner's, with these docs), and the published pages load nothing from other origins: fonts are self-hosted, and there are no CDNs, embeds, or trackers.
3. **Readers aren't tracked.** Public and shared pages set no cookies. The only browser storage is a share reader's own session: a non-extractable key in IndexedDB with the grant's ID or the name's lookup (not the name, though it can be recovered by guessing names) and its expiry, found by a random record ID in that tab's `sessionStorage`, kept past the tab only if they ask to be remembered, and the time of their last sign-out in `localStorage` (D-125). Script on the same `<user>.github.io` origin can use that key while it's stored, but can't copy it out. In the app, the browser keeps only the notes written there, its state, and a remembered vault key if the owner chose it, and sends none of it anywhere.
4. **Private by default.** New notes are private (D-05). Agents start with no private access (D-45). Synced preferences live in the private repository (D-46). Notes imported from a browser are private unless the user chooses public (FRE-10).
5. **What a public notes repository and its site reveal,** listed so users can decide: the names of their two repositories (including the private one, in `.gitmodules`), the full history of public notes (including deleted ones), the time of each publishing commit and deploy, that the site has a vault, and the existence and size of sealed files. The private repository can be given any name.
6. **Commits use the noreply address** by default (first run, identity step).

### Proposed rewrite integration

The [rewrite provider contract](rewrite-providers.md#policy-first) is a draft exception proposal, **not an enabled capability or amendment to the shipped commitments above**. Focus Notes would be a client of an explicitly approved external app/API only, never a model installer or host. Its main-process [egress/credential boundary](rewrite-providers.md#routing-and-egress), [private-note consent matrix](rewrite-providers.md#consent-and-private-notes) and [OS-encrypted isolated history](rewrite-history.md#private-isolation) must pass the owner gate before any real send. That gate includes updating privacy claims and this data inventory together; fake-first specification work authorizes neither calls nor credentials. No telemetry remains unconditional.

## Supply chain and releases

- Dependencies are pinned by lockfile and updated by Dependabot pull requests that must pass CI. The license check (D-20) runs on every change.
- Every GitHub Action is pinned to a full commit SHA.
- Releases are built in GitHub Actions only, never on a developer's computer. Each one has SHA-256 checksums, a CycloneDX SBOM, and GitHub artifact attestations (build provenance). Installers are code-signed and macOS builds are notarized once signing is in place (DSK-07, D-51). Until then, the release notes say the build is unsigned and show the checksum to verify.
- Updates are checked by electron-updater against GitHub Releases and verified before installing.
- Repository settings: branch protection on `main` (pull request and passing checks), secret scanning with push protection, CodeQL, and the OpenSSF Scorecard.

## Vulnerability reporting and response

- `SECURITY.md` explains how to report privately through GitHub's private vulnerability reporting. We aim to acknowledge within 7 days.
- **A share secret leaks:** withdraw the audience. It stops opening at the next deploy.
- **The share-link key leaks:** Settings → Workspace → *Rotate share-link key* replaces the deploy key and the secret.
- **The vault passphrase leaks:** set a new one in the desktop app; the next deploy seals with fresh keys under it, and remembered keys stop working.
- **A token leaks** (desktop): revoke it on GitHub, then sign in again.
- **A bad release:** template instances, which pin the web app's version, aren't affected until they merge an update. A fixed release supersedes it, and the advisory is published on GitHub.
